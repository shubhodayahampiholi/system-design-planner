# Scoping Decisions Log

- 2026-08-15 [native tooling scope]: Client's technical answers (serverless compute, Private Link/NCC, Mosaic AI Provisioned Throughput terminology) confirm they want the Databricks-native stack (Databricks Apps, Mosaic AI Vector Search/Model Serving, Unity Catalog) rather than the Azure-native stack (Foundry Agent Service, Azure AI Search). Treat "native tooling" as Databricks-native by default for this engagement unless told otherwise.
- 2026-08-15 [network compute plane]: Agent compute stays serverless (no VNet injection); private VNet resources are reached via Private Link + Network Connectivity Config (NCC), not by injecting Databricks into the customer VNet.
- 2026-08-15 [model serving throughput mode]: Enterprise-wide, moderate-volume usage — client prefers Provisioned Throughput serving over pay-per-token for predictable cost/latency. No hard SLA number defined yet.
- 2026-08-15 [private DB access pattern]: The private database is accessed read-only, at query time, via an agent tool call — it is supplementary lookup data, not part of the RAG vector index/corpus.
- 2026-08-15 [governance data readiness]: The governed customer data for RAG already exists in Unity Catalog as Delta tables, ready to be indexed — no migration/ingestion design needed for the source data itself.
- 2026-08-18 [external partner auth to governance layer]: External partner integrations authenticate via Databricks-native UC service principals + OAuth M2M (one SP per partner org, least-privilege grants, Delta Sharing for data-pull, Unity AI Gateway for tool/agent-call patterns) — Foundry's presence does not change this since Foundry is not the governance/identity plane. PATs and shared credentials are excluded.
- 2026-08-18 [open item: partner integration pattern]: Not yet confirmed whether the new external partner integration is data-pull (Delta Sharing), tool/agent-call (OAuth M2M + UC AI Gateway), or human SSO (Entra B2B) — each implies a different mechanism; must be resolved before final design.
- 2026-08-18 [open item: partner inbound network path]: Existing serverless + Private Link/NCC decision only covers Databricks' outbound reach into private VNet resources; it does not define how an external partner's inbound traffic reaches the governance layer (public internet+OAuth/mTLS vs. ExpressRoute/VPN vs. APIM front door) — still undecided.
- 2026-08-18 [open item: Databricks-Foundry connector policy parity]: Whether data flowing through the Databricks↔Foundry connector needs a separate Purview-side policy, or UC policy suffices end-to-end, is unresolved. Not blocking today's Databricks-native designs, but becomes load-bearing if any partner-facing or governed data path is later exposed via Foundry/Azure AI Agent Service.
- 2026-08-18 [vendor doc corpus versioning]: Third-party vendor's nightly batch-imported support docs carry a stable document_id + version number in file metadata on every send, including corrections. Ingestion design keys off document_id/version for upsert/supersede logic rather than content-hash or fuzzy dedup.
- 2026-08-18 [open item: vendor doc landing mechanism/network path]: Not yet confirmed how the vendor's nightly batch files physically arrive (push to a storage account, SFTP, API pull) or what the inbound network path is. May or may not be the same integration as the "external partner inbound network path" open item above — needs confirmation, don't assume same vendor/mechanism.
- 2026-08-18 [open item: vendor doc format & retraction signal]: Assumed vendor support docs are PDF/scanned (drives choice of ai_parse_document) — needs confirmation. Also no known signal for a full document retraction/tombstone (only version-bump corrections are confirmed); design currently has no handling for a vendor fully withdrawing a doc.
- 2026-08-18 [open item: embedding endpoint throughput mode]: The Provisioned Throughput preference on record is for the primary/steady LLM serving workload. Whether embedding calls for this nightly-batch, bursty vendor-doc ingestion should also use Provisioned Throughput vs. pay-per-token Foundation Model APIs is a separate, unresolved cost decision — don't assume the PT decision auto-extends to embedding endpoints.
- 2026-08-18 [open item: vendor doc retrieval eval set]: No held-out query-to-document pairs exist yet for recall@k/MRR evaluation of the vendor doc RAG index. Need client-provided source (e.g., support ticket-to-KB-article logs, or SME-curated Q&A) before a baseline can be stated.
- 2026-08-19 [docs-assistant corpus format]: The "assistant over docs" app's corpus is PDFs already landed in a Unity Catalog Volume (not a live vendor push feed) — confirms ai_parse_document (or similar PDF extraction) is needed; storage/landing mechanism itself is a Volume, so prior "vendor doc landing mechanism" open item may be moot for this app specifically.
- 2026-08-19 [docs-assistant audience & scale]: Internal employees only (no external partner access via this assistant), ~100 concurrent users — sized as a single-region, moderate-concurrency deployment, not enterprise-massive-scale.
- 2026-08-19 [docs-assistant agent pattern]: Confirmed RAG-based with multi-step reasoning (not simple single-shot retrieve-then-answer) — implies an agent/orchestrator loop (e.g., query planning, multi-hop retrieval, or tool chaining) rather than a single retrieval call.
- 2026-08-19 [open item: docs-assistant corpus relationship to vendor doc pipeline]: Not yet confirmed whether this PDF-in-Volume corpus is the same vendor doc corpus discussed earlier (nightly batch, document_id/version metadata) or a separate/static corpus — affects whether the versioning/upsert ingestion design carries over.
- 2026-08-19 [docs-assistant tool scope]: Confirmed retrieval-only against the PDF corpus — no private-DB lookup tool in this agent. Single-tool RAG agent, not a tool-router.
- 2026-08-19 [docs-assistant multi-step definition]: "Multi-step" = query decomposition (break complex question into sub-queries, retrieve per sub-query, synthesize) — not re-ranking, self-critique, or a multi-agent verification pipeline. Sizes the orchestration as a single agentic loop, not a multi-agent system.
- 2026-08-19 [docs-assistant embedding model]: Recommended `databricks-gte-large-en` (Foundation Model APIs) as default over `databricks-bge-large-en` — 8192-token window avoids truncating page/paragraph-level PDF chunks (BGE is 512 tokens), and Databricks positions GTE specifically for RAG retrieval. Plan to use Vector Search's Databricks-managed embeddings mode (index points at GTE directly) rather than a manual embed step in the ingestion job.
- 2026-08-19 [docs-assistant embedding throughput mode]: Recommendation (pending client sign-off) is pay-per-token Foundation Model API for the nightly batch embedding calls, not Provisioned Throughput — embeddings are cheap/bursty; PT stays reserved for the steady-state LLM serving endpoint.
- 2026-08-19 [open item: docs-assistant language scope]: Assumed English-only PDFs since the curated GTE/BGE embedding endpoints are English-only. Needs confirmation — if multilingual content exists, requires a self-deployed multilingual embedding model instead.
- 2026-08-19 [vendor doc chunking strategy]: ai-ml-specialist recommendation — structure-aware chunking (per section/heading, tables kept intact as their own chunk) as primary strategy, with fixed-size (~512 tokens, 10-15% overlap) as fallback only within long unstructured prose. Fixed-size-by-default rejected because support docs likely contain tables/numbered steps that a flat window would split mid-structure.
- 2026-08-19 [vendor doc chunk metadata/upsert]: Each chunk row carries document_id, version, and a stable section/anchor id. Supersede logic = merge/upsert keyed on (document_id, version, chunk_anchor): on new version, retire all prior-version chunks and insert new version's chunk set — not row-by-row diff, not append-only.
- 2026-08-19 [open item: vendor doc corpus — full retraction/tombstone gap]: Confirmed real gap (not just theoretical) — a vendor fully withdrawing a document_id with no new version sent leaves its chunks live in the index indefinitely with no removal signal. Needs a resolution path before production launch.
